# 问题与报告契约

## 0. 机器校验

输出报告前，必须用脚本校验问题清单，不通过不得出报告：

```bash
python3 <SKILL_ROOT>/scripts/check-findings.py <findings.json> \
  --repo-root <repo> --head <source-sha> --change-map <work-dir>/change-map.json
```

它检查本文中所有能机器判定的部分：`severity` 只能是 `P0`/`P1`/`P2`，`confidence`
只能是 1-10 的整数且低于 7 不得上报，`trigger`/`impact`/`evidence`/`action` 必填
且为简体中文，行锚点在锁定 head 上真实存在且落在变更行区间（含 ±10 行容差）内，按规范
`fingerprint` 去重，以及问题数量上限与 P0 保留规则。退出码 `4` 表示违反契约。

**锚点越界不等于问题不成立。** 被签名变更打到的未改调用方、该加在函数入口的守卫、被删测试
覆盖的契约、审计边界内的既有代码，都会落在变更行之外。这类问题必须填写 `anchor_note`（简体
中文，一句话说明为什么锚在这里、它与本次变更的因果关系），而不是删掉问题去换取校验通过。
校验失败时的正确动作是修锚点或补 `anchor_note`；靠删问题凑到 `exit 0` 属于违反契约。

脚本不判断问题是否成立——那仍然由证据阶段负责。

## 1. 问题准入门槛

可报告的问题必须同时满足以下条件：

- **当前范围：** 问题存在于锁定的 patchset，或用户要求的本地/完整文件范围内。
- **变更行为：** 问题由本次变更引入、暴露或显著恶化。对于完整文件/仓库审计，问题必须位于明确的审计边界内。
- **触发条件：** 有具体输入、状态、时序、调用方、部署条件或攻击路径。
- **影响：** 有可观察的正确性、安全性、兼容性、运维、测试可靠性或实质性能后果。
- **锚点：** 精确的仓库相对文件路径和当前行号，或最小有效行范围。锚点落在变更行之外时，
  用 `anchor_note` 说明它与本次变更的因果关系；不得为了对齐变更行而挪到错误位置，也不得因此丢弃问题。
- **行动：** 能解决根因且不重新设计无关代码的最小修复方向。
- **置信度：** 经过直接上下文验证后至少达到 7/10，并以 1-10 的整数记录。
- **词汇表：** `severity` 只能取 `P0`/`P1`/`P2`。不得使用 `high`/`medium`/`low` 或其他自造词汇，也不得用文字替代数值置信度。

验证输出本身不是问题。只有确认失败检查源于本次评审变更，而非环境、过期生成物、无关本地修改或既有失败后，它才构成问题。

文档变更适用同一套门槛，只是触发条件与影响换成读者视角：**触发条件是读者按文档执行或依赖它做出的具体动作，影响是由此产生的可观察后果**。判定口径见 [discovery-and-coverage.md](discovery-and-coverage.md) 第 3.5 节。严重级别参考：

| 级别 | 文档缺陷 |
|---|---|
| `P0` | 明文有效凭据或密钥；runbook 步骤按序执行会造成生产中断或数据丢失 |
| `P1` | 文档与代码不符，会让读者做出错误集成或错误操作；安全/权限相关指引是错的；迁移或回滚顺序写反 |
| `P2` | 失效引用、已删除符号的残留提及、示例中的小错误 |

措辞、语气、术语偏好、篇幅、章节顺序、拼写语法（除非改变技术含义）和工具处理的格式，一律不构成问题，也不得写成建议项凑数。

## 2. 待确认风险

置信度为 `5-6` 的候选只有在同时具备具体代码路径、触发条件和实质潜在影响，但仍缺少一个无法安全取得的关键事实时，才可以作为 `待确认风险` 输出。

待确认风险：

- 不是 P0-P2 缺陷，不计入缺陷数量，也不单独阻止合并
- 不得发布为 MR/PR 行内评论
- 必须写明缺失事实以及确认或排除它的最小动作
- 默认最多保留三条，按潜在影响排序
- 不得容纳泛化担忧、个人偏好、没有代码路径的假设或低于 5/10 的推测

## 3. 严重级别与置信度

| 严重级别 | 含义 |
|---|---|
| `P0` | 确定或极可能发生的安全突破、数据损坏/丢失、核心路径崩溃/中断或不可逆故障；阻止合并/发布。 |
| `P1` | 在明确条件下会发生的正确性、并发、兼容性、回滚、隔离或运维故障；应在合并前修复。 |
| `P2` | 已证明触发路径、影响较低的真实缺陷或防御缺口；合并风险可接受时可以后续跟进。 |

置信度必须与严重级别相互独立：

- `9-10`：已从代码证明或直接复现
- `7-8`：证据充分，仅少量依赖运行时/环境条件
- `5-6`：看似合理但缺少关键事实；不得作为问题报告
- `1-4`：推测；删除

不得为了让关注点显眼而夸大严重级别。缺失的外部事实应放入限制或假设，不应放进缺陷列表。

## 4. 优先级

默认最多报告五个问题，先按严重级别、再按置信度排序。绝不能为了满足数量限制而省略已验证的 `P0`；如果仍有五个以上根因，保留全部 `P0` 和其他风险最高的问题，并说明未展开低风险问题。

按根因去重。同一缺陷出现在多行时，选择真正应修复的位置作为锚点，并在证据中说明受影响路径。

## 5. 结论

- `Needs changes`：至少有一个已验证的 `P0` 或 `P1`。
- `可以合并，但建议跟进`：只剩已验证的 `P2` 问题。
- `未发现已证实阻断问题，但存在待确认风险`：没有 P0/P1，但仍有置信度 5-6 的实质候选或重要覆盖限制。
- `LGTM`：没有可报告问题或待确认风险，并且变更组、五视角、二级反例、复核轮次、跨组契约和风险验证均达到 `discovery-and-coverage.md` 的完成门槛。
- `无法完成可靠 Review`：范围/证据不足；必须准确说明缺失内容。

如果问题涉及未被测试覆盖的契约，测试通过不能把 `Needs changes` 升级为可合并。如果触发条件已由代码证明，测试缺失或受阻也不会自动降低该问题的可信度。

## 6. 中文报告结构

先给结论。除 `范围与限制` 外，空章节应省略。

```markdown
## 结论

Needs changes — [一句话说明最大风险]

## 问题

### [P1][置信度 9/10] `path/file.go:42` 标题

- 触发条件：[具体输入、时序或调用路径]
- 问题与影响：[发生什么，用户/数据/兼容性/运维后果是什么]
- 证据：[关键代码关系、复现或验证结果]
- 建议：[最小修复方向；不替作者重做无关设计]

## 验证

- `go test ./path/...`：通过
- `go test -race -count=1 ./path/...`：未运行；原因是……

## 待确认风险

### [置信度 6/10] `path/file.go:88` 标题

- 已知路径：[代码已经证明的部分]
- 缺失事实：[尚未取得的运行时/外部契约]
- 潜在影响：[如果事实成立会发生什么]
- 确认方式：[最小验证动作]

## 评审覆盖

- 变更组：[已覆盖的行为组]
- 独立视角：Correctness / Architecture / Compatibility-Ops / Security-Abuse / Tests
  （纯文档变更改为列出第 3.5 节检查集的逐项结论）
- 复核轮次：[已完成的轮次；小变更含证伪轮，大变更含高风险组二次发现与全局复核]
- 失败场景：[已追踪的关键反例]
- 跨组校验：[结果或不适用原因]

## 范围与限制

- 范围：`<base-sha>...<source-sha>`，patchset N
- 已检查：[文件/包/契约摘要]
- 限制：[未取得的外部事实、未运行的高成本检查；没有则写 `无`]
```

如果没有问题，写明 `本次范围内未发现需要报告的 P0-P2 问题`，同时披露精确范围、变更组、关键失败场景、五个独立视角、复核轮次、跨组校验和验证限制。覆盖不足时不得给出 `LGTM`。

不得用泛泛表扬、工作流程复述或没有证据的 `PASS` 清单填充报告。

当用户要求可维护性、简化、架构、重构或可直接修复的深度时，应用 [maintainability-and-refactoring.md](maintainability-and-refactoring.md)。把具体的非缺陷观察放在 `建议项（不影响合并结论）` 下；绝不能用它们降低 `LGTM` 结论或抬高 P0-P2 数量。只有用户要求查看或应用修复时，才提供替换代码或聚焦 diff。

## 7. 可直接发布的评论措辞

用户要求可直接粘贴的评论时，给出精确的当前位置和简洁中文措辞：

```markdown
`path/file.go:42`

[P1] 这里从 `context.Background()` 派生超时会切断请求取消和 request-scoped trace/tenant 值；客户端断开后存储调用仍会继续。建议改为 `context.WithTimeout(r.Context(), ...)`，并补一个取消传播回归测试。
```

发布这些评论属于单独授权的操作，受 [scope-and-permissions.md](scope-and-permissions.md) 约束。待确认风险永远不得发布为行内评论。
