# 缺陷发现与覆盖契约

本文负责提高缺陷召回率。它只规定如何发现、反证和覆盖，不降低 `finding-and-report-contract.md` 的正式问题门槛。

## 1. 两阶段模型

评审必须明确分为两个阶段：

1. **发现阶段：** 主动构造可能失败的执行路径，允许保留尚未完全证明的候选。
2. **证据阶段：** 对候选读取调用方、状态、副作用、外部契约和测试，证实或证伪后再决定是否进入最终报告。

不得在发现阶段直接使用“置信度不足所以不看了”终止调查。置信度是证据阶段的输出，不是发现阶段的过滤器。

## 2. 变更地图

先把 diff 按行为、调用链或共享契约划分为变更组。每组至少记录：

- 变更想改变的行为及入口
- 直接调用方、实现方和数据所有者
- 读取、写入、外部调用、异步任务等副作用顺序
- API、IDL、配置、schema、缓存、事件或部署契约
- 已有测试证明了什么，以及没有证明什么

文件目录只是线索，不是分组依据。一个共享类型、接口、配置或 schema 可以同时属于多个变更组。

## 3. 四个独立评审视角

每个实质变更组都应用以下视角；不适用时记录 `N/A` 和理由，不能用泛化的 `PASS` 填充。

### Correctness

检查行为、边界、错误传播、状态迁移、副作用顺序、重试、幂等、并发、取消、资源生命周期和数据一致性。

### Architecture

检查职责所有权、依赖方向、事务边界、抽象泄漏和复杂度是否隐藏行为缺陷。纯偏好不进入 P0-P2；只有具体边界破坏或维护风险才形成候选。

### Compatibility-Ops-Safety

检查 API/IDL/config/data 兼容、迁移、混合版本、回滚、权限与隔离、日志/指标、启动关闭、失败恢复和不可逆副作用。

### Tests

检查当前测试能否对错误实现失败，而不只是成功执行。测试候选必须说明变化的契约、证明所属层、会漏掉的具体错误实现和最小补强动作。

这四个视角借鉴不同角色的独立责任，但不要求特定 Agent、模型或运行时。最终收敛不得替代任何视角重新发现问题。

## 4. 反例驱动发现

根据变更实际触及的风险，主动选择反例，不要求机械穷举：

- 首次调用、重复调用、重试和恢复后的调用是否一致
- 成功、拒绝、超时、取消、部分失败和补偿失败分别留下什么状态
- 输入为空、零值、非法、超长、重复、乱序或位于边界时发生什么
- 并发调用、关闭、leader 切换或 lease 失效时所有权是否仍成立
- 一个字段/资源失败时，其他字段/资源是否被错误回退、覆盖或删除
- 旧调用方、新调用方、混合版本、升级后回滚是否仍能读写同一数据
- 能力探测、unknown/default 分支和降级路径是否真正安全
- 配置缺失、显式零值、环境覆盖和不同部署模板是否语义一致

对每个高风险变更组至少完成一个与 happy path 不同的失败场景追踪；这是覆盖要求，不是问题数量要求。

## 5. 候选台账

对非平凡 MR，在仓库外的临时评审目录维护候选台账。格式可用 Markdown 或 JSONL，但每条至少包含：

- `group`：所属变更组
- `lens`：四个视角之一
- `anchor`：候选代码位置
- `hypothesis`：可能错误的行为
- `trigger`：具体输入、状态或时序
- `impact`：潜在可观察后果
- `evidence_for`：支持证据
- `evidence_against`：反证或保护机制
- `missing_fact`：仍缺少的关键事实
- `status`：`confirmed` / `open` / `rejected`

台账是评审过程证据，不应写入被评审仓库，也不应把每条候选都暴露给用户。

状态规则：

- `confirmed`：满足正式问题准入门槛。
- `open`：有具体代码路径和实质影响，但仍缺一个无法安全取得的关键事实。
- `rejected`：已由调用方、保护条件、版本语义、测试或当前 patchset 证伪；记录一句淘汰理由。

## 6. 证伪优先

报告候选前，主动寻找能让它不成立的证据：

- 当前调用方是否已经保证前置条件
- 事务、defer、补偿、幂等键或所有权检查是否覆盖失败路径
- 外部库和目标 Go 版本是否提供所依赖保证
- 同一行为是否由更合适层的测试可靠证明
- 问题是否只存在于旧代码、删除代码或当前 patchset 已修复部分

找不到反证不等于问题成立；仍必须证明触发和影响。

## 7. 规模与独立复核

### 小变更

文件数不超过 5 且总变更行数不超过 500：

- 一次主调用链评审
- 一次独立的反例与跨契约复核

第二次复核不能只是重读结论，应从不同视角检查失败路径、调用方和未覆盖契约。

### 大变更

文件数超过 5 或总变更行数超过 500：

- 按行为、调用链或共享契约分组，确保每个文件至少属于一组
- 每组执行四视角发现和证据筛选
- 接口、共享类型、配置和 schema 等边界文件按需要跨组出现
- 最后检查跨组 API、状态、副作用、配置、生成代码、部署和测试契约

仅在用户和运行时明确允许时并行委派。不能委派时，主 Agent 使用分离的串行轮次和独立记录完成同样工作；不得抽样、合并掉某组或省略跨组检查。

## 8. 评审完成门槛

给出最终结论前必须满足：

- 精确范围和 patchset 仍然新鲜
- 每个变更组均被覆盖，没有未解释的文件
- 四个视角均为有证据的 `checked`、`risk` 或 `N/A`
- 每个高风险组至少追踪一个失败场景
- 所有候选均为 `confirmed`、`open` 或带理由的 `rejected`
- 已运行与风险相称的验证，或明确说明无法运行的原因
- 已执行跨组复核；不适用时说明原因

未满足时不得用 `LGTM` 掩盖覆盖缺口。应输出“无法完成可靠 Review”或“未发现已证实阻断问题，但存在待确认风险/覆盖限制”。
