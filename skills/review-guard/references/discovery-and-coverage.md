# 缺陷发现与覆盖契约

本文负责提高缺陷召回率。它只规定如何发现、反证和覆盖，不降低 `finding-and-report-contract.md` 的正式问题门槛。

## 1. 两阶段模型

评审必须明确分为两个阶段：

1. **发现阶段：** 主动构造可能失败的执行路径，允许保留尚未完全证明的候选。
2. **证据阶段：** 对候选读取调用方、状态、副作用、外部契约和测试，证实或证伪后再决定是否进入最终报告。

不得在发现阶段直接使用“置信度不足所以不看了”终止调查。置信度是证据阶段的输出，不是发现阶段的过滤器。

## 2. 变更地图

先运行 `scripts/change-map.py` 得到机器事实，再在其之上划分变更组；不要用一串探索性 grep 重新发现脚本已经给出的东西：

```bash
python3 <SKILL_ROOT>/scripts/change-map.py \
  --repo-root <repo> --base <base-sha> --head <head-sha> --output <work-dir>/change-map.json
```

它给出按 package 分组的变更文件、新增/删除/**签名变化**的声明及是否导出、struct 字段与 tag 的增删改、每个导出符号在仓库内的引用与是否跨 package、被删除的测试函数、每个 module 的 Go 语言版本、hunk 行区间，以及 IDL/schema/deploy/CI/config/docs 信号。

这些是线索不是结论：声明由正则提取，引用是文本匹配，可能含同名符号。据此提出的候选仍必须回源码证实。

在脚本输出之上，把 diff 按行为、调用链或共享契约划分为变更组。每组至少记录：

- 变更想改变的行为及入口
- 直接调用方、实现方和数据所有者
- 读取、写入、外部调用、异步任务等副作用顺序
- API、IDL、配置、schema、缓存、事件或部署契约
- 已有测试证明了什么，以及没有证明什么

文件目录只是线索，不是分组依据。一个共享类型、接口、配置或 schema 可以同时属于多个变更组。

## 3. 五个独立评审视角

每个实质变更组都应用以下视角；不适用时记录 `N/A` 和理由，不能用泛化的 `PASS` 填充。

### Correctness

检查行为、边界、错误传播、状态迁移、副作用顺序、重试、幂等、并发、取消、资源生命周期和数据一致性。

### Architecture

检查职责所有权、依赖方向、事务边界、抽象泄漏和复杂度是否隐藏行为缺陷。纯偏好不进入 P0-P2；只有具体边界破坏或维护风险才形成候选。

### Compatibility-Ops

检查 API/IDL/config/data 兼容、迁移、混合版本、回滚、日志/指标、启动关闭、失败恢复和不可逆副作用。

### Security-Abuse

安全与兼容运维的推理方法不同，因此单列一个视角：兼容视角问“旧调用方还能用吗”，安全视角问“恶意调用方能拿到什么”。不要用前者代替后者。

从信任边界出发，沿身份 -> 校验 -> 决策 -> 资源 -> 副作用追踪，逐段确认：

- 身份从哪来，是否可由调用方伪造或省略
- 校验的是**所有权**还是仅仅**存在性**：租户/workspace/session/namespace 边界是否对每一个调用方可控的 ID 都验过，还是只验了其中一个
- 复合标识里是否有分量绕过了鉴权（例如只鉴权父 ID，子 ID 直传下游）
- 外部可控的数量、大小、递归深度、fan-out 和解压比例是否有上限
- secret/token 在配置、日志、错误、URL、持久化、遥测和下游请求中的流向
- 注入、路径遍历、SSRF、不安全反序列化与重定向策略在**实际使用点**是否成立

细则见 [go-review-checks.md](go-review-checks.md) 第 6 节。严重级别按真实攻击路径和影响判定：**可由外部调用方触发的越权或跨租户读写不是 P2**。

### Tests

检查当前测试能否对错误实现失败，而不只是成功执行。测试候选必须说明变化的契约、证明所属层、会漏掉的具体错误实现和最小补强动作。

这五个视角借鉴不同角色的独立责任，但不要求特定 Agent、模型或运行时。最终收敛不得替代任何视角重新发现问题。

### 机械 N/A 判定

以下情形直接判 `N/A` 并记一句理由，不必逐个视角展开推理。判定依据来自 `change-map.json`，不是印象：

| 变更组特征 | 可直接 N/A 的视角 |
|---|---|
| 组内只有 `signals.docs` 列出的文件，且无 Go 变更 | Correctness、Tests |
| 组内只有 `_test.go` 变更，且不改变被测契约 | Architecture、Compatibility-Ops |
| 组内声明全部未导出，`references` 显示无跨 package 引用，且不触及 IDL/schema/config/deploy 信号 | Compatibility-Ops |
| 纯映射/纯函数变更：无 goroutine、channel、锁、`context`、I/O 和包级状态 | 反例清单中的并发、取消、生命周期条目 |
| 组内不触及任何信任边界：无外部输入入口、无身份/租户/权限判定、无 secret、无外部可控的数量或大小 | Security-Abuse |
| `go_modules` 显示的语言版本已排除某类问题（如每轮独立 range 变量） | 该版本相关检查 |

任一特征不成立就必须展开该视角。N/A 只免除推理，不免除记录；也绝不能用它跳过存在导出符号、共享契约、状态或信任边界的变更组。Security-Abuse 的 N/A 门槛最严：只要变更组里有任何一个调用方可控的输入，就必须展开。

## 3.5 文档变更评审

`change-map.json` 的 `docs_only` 为真时（变更集里没有任何代码文件），走本节的短路径，不要把面向代码的机器空转一遍。文档不是零风险，但它的风险形状和代码不同。

### 短路

跳过：五视角逐组展开、非引用类的二级反例、`go test`/`-race`/lint 等代码验证、针对代码路径的证伪轮。

保留：范围锁定、`doc_references` 核对、下面的检查集、问题准入门槛和 `check-findings.py` 机器校验。

**混合变更集不走短路。** 文档文件归入它们所记录的契约所属的变更组，和代码一起按五视角评审；文档与代码不一致本身就是该组的兼容性候选。

### 检查集

依据 `change-map.json` 的 `doc_references`，逐项核对而不是通读润色：

| 检查 | 机器线索 | 要证明什么 |
|---|---|---|
| 文档与代码事实不符 | `identifiers_not_found_in_code`、`env_vars_not_found_in_code` | 文档命名的符号、flag、环境变量、endpoint 或默认值在当前 head 的**代码**里确实存在且语义一致。脚本只在文档之外搜索，因此"只出现在文档里"本身就是候选；仍要区分拼写错误、已删除，还是本就属于外部系统 |
| 引用失效 | `missing_paths` | 相对链接、文件路径、ADR 编号在锁定 head 上真实存在 |
| 明文凭据与敏感数据 | `possible_plaintext_secrets` | 示例里的 token/密码/密钥是占位符还是真值；是否泄露内部主机名、客户数据或真实账号 |
| 可执行内容有害或错误 | `code_fence_languages` 含 `bash`/`sh`/`sql`/`yaml` | runbook 步骤按序执行会不会造成中断或数据丢失；迁移/回滚顺序是否正确；命令是否缺少 namespace、`--dry-run` 或确认步骤 |
| 示例代码错误 | `code_fence_languages` 含 `go` | 示例能否编译、是否演示了被文档本身警告的错误用法、是否使用了当前版本已移除的 API |
| 契约文档与实现冲突 | ADR/设计文档路径 | 文档声明的决策与当前代码实际行为是否矛盾；矛盾时指出是文档过时还是实现跑偏 |
| 生成物来源 | `signals.generated` | 手改了由源定义生成的文档，而没有改源 |

### 不构成问题

措辞、语气、术语偏好、篇幅、章节顺序、是否该配图、拼写与语法（除非改变技术含义）、由工具处理的格式。这些一律不进问题列表，也不能写成"建议项"来凑数。

覆盖门槛不因为"只是文档"而降低：`doc_references` 的每一项异常都必须给出结论或不适用理由。核对完成且无可报告问题时，正常给出 `LGTM`。

## 4. 反例驱动发现

根据变更实际触及的风险，主动选择反例，不要求机械穷举：

- 首次调用、重复调用、重试和恢复后的调用是否一致
- 成功、拒绝、超时、取消、部分失败和补偿失败分别留下什么状态
- 输入为空、零值、非法、超长、重复、乱序或位于边界时发生什么
- 并发调用、关闭、leader 切换或 lease 失效时所有权是否仍成立
- 一个字段/资源失败时，其他字段/资源是否被错误回退、覆盖或删除
- 旧调用方、新调用方、混合版本、升级后回滚是否仍能读写同一数据
- 能力探测、unknown/default 分支和降级路径是否真正安全
- 配置缺失、显式零值、环境覆盖和不同部署模板是否语义一致

每个高风险变更组都要追踪与 happy path 不同的失败场景，且必须把命中的二级反例逐条走完；「已经追踪过一个失败场景」不是结束该组发现的理由。这是覆盖要求，不是问题数量要求。

### 按信号触发的二级反例

上面是通用清单。`change-map.json` 命中以下信号时，**必须**再展开对应的二级反例，不能以“已做过一个失败场景”为由跳过：

| 触发信号 | 必须追踪的反例 |
|---|---|
| `signals.schema` 或持久化路径变更 | 部分写入后进程崩溃；唯一约束冲突；事务内发起外部调用后事务回滚；读写分离下的复制延迟；新字段被旧版本仓储静默丢弃 |
| `struct_fields.tag_changed` / `removed`，或 `signals.idl` | 新字段被旧消费方丢弃；枚举新增值在旧版本落入 `default`；字段名大小写在生产方/消费方/白名单/前端投影之间不一致；默认值从“未设置”变成显式零值 |
| `declarations.signature_changed` 中有导出符号，且 `references.cross_package` 为真 | 未随本次变更更新的调用方在编译期是否可见失败；行为契约（错误语义、副作用顺序、nil 语义）是否被静默改变 |
| 变更组存在信任边界（Security-Abuse 未判 N/A） | 只持有子资源 ID 的越权调用方；跨租户 ID 直接引用；伪造或省略身份；重放同一幂等键；超长/超量/深层嵌套输入；错误信息回显内部状态 |
| 组内存在 goroutine、锁、`context` 或共享状态 | 两个请求并发创建同一资源；锁外读取后加锁写入的 check-then-act 窗口；取消与 `defer` 清理竞争；lease 有效期与扫描周期相等或更短导致的重复认领；goroutine 泄漏在单测里不可见 |
| `signals.deploy` 或 `signals.config` | 启动顺序依赖；优雅关闭期间到达的新请求；健康检查早于依赖就绪；同一配置键在 Go 结构体、示例、Helm 模板和环境变量间语义不一致 |
| 变更组新增或修改了带持久状态的累加器、latch、窗口、游标或状态机，或代码注释/文档为它声明了不变量（如「只可高报不可少报」「不可信的值一次都不发布」「该值单调不减」） | 先把声明的不变量原文抄进台账，再列出该状态的全部字段与迁移（包括 latch 置位后由谁清除、零值含义、跨 goroutine 读写时序），逐条迁移问「它能否违反这条不变量」；再问这条不变量在**发布链路末端**是否仍然成立（聚合、窗口、导出间隔、下游默认值可能把它抵消掉）。逐条给结论 |
| `removed_test_functions` 非空 | 被删测试原本证明的契约现在由谁证明；行为是被有意删除还是覆盖被悄悄降低 |

命中多个信号时全部展开。每条二级反例要么给出追踪结论，要么记录为什么在当前范围内不可达。

除状态机/不变量那一行外，触发信号都来自 `change-map.json`。那一行的触发条件只能靠读新增源码判定：新增文件里出现带字段的状态结构、latch 布尔、generation/序号、窗口或游标时即视为命中，不得因为脚本没有对应字段就跳过。

## 5. 候选台账

对非平凡 MR，在仓库外的临时评审目录维护候选台账。格式可用 Markdown 或 JSONL，但每条至少包含：

- `group`：所属变更组
- `lens`：五个视角之一
- `anchor`：候选代码位置
- `hypothesis`：可能错误的行为
- `trigger`：具体输入、状态或时序
- `impact`：潜在可观察后果
- `evidence_for`：支持证据
- `evidence_against`：反证或保护机制
- `missing_fact`：仍缺少的关键事实
- `status`：`confirmed` / `open` / `rejected`

台账是评审过程证据，不应写入被评审仓库，也不应把每条候选都暴露给用户。

状态规则：

- `confirmed`：满足正式问题准入门槛。
- `open`：有具体代码路径和实质影响，但仍缺一个无法安全取得的关键事实。
- `rejected`：已由调用方、保护条件、版本语义、测试或当前 patchset 证伪；记录一句淘汰理由。

## 6. 证伪优先

报告候选前，主动寻找能让它不成立的证据：

- 当前调用方是否已经保证前置条件
- 事务、defer、补偿、幂等键或所有权检查是否覆盖失败路径
- 外部库和目标 Go 版本是否提供所依赖保证
- 同一行为是否由更合适层的测试可靠证明
- 问题是否只存在于旧代码、删除代码或当前 patchset 已修复部分

找不到反证不等于问题成立；仍必须证明触发和影响。

## 7. 规模与独立复核

每一轮都必须留下独立记录。后一轮不得先读前一轮的结论再“确认一遍”——那不是复核，是自我确认。

### 小变更

文件数不超过 5 且总变更行数不超过 500：

1. 一次主调用链评审
2. 一次独立的反例与跨契约复核，从不同入口顺序进入，检查失败路径、调用方和未覆盖契约
3. **一次证伪轮**：只针对已进入 `confirmed` 的候选，逐条按第 6 节主动找反证。这一轮的目标是**推翻**结论，不是补充证据；被推翻的转 `rejected` 并记理由

### 大变更

文件数超过 5 或总变更行数超过 500：

1. 按行为、调用链或共享契约分组，确保每个文件至少属于一组
2. 每组执行五视角发现和证据筛选
3. **高风险组的第二次独立发现轮**：对命中二级反例信号、或含导出契约变更、或 Security-Abuse 未判 N/A 的组，换一个入口顺序重做一次发现。高风险组的路径依赖最强，一次遍历容易只看到第一条想到的链路
4. 接口、共享类型、配置和 schema 等边界文件按需要跨组出现
5. 检查跨组 API、状态、副作用、配置、生成代码、部署和测试契约
6. **收敛前的全局复核**：跨组一致性再过一遍，并抽样复检已 `rejected` 的候选——尤其是以“调用方保证了前置条件”为由淘汰的那些，确认该保证在所有调用方上都成立

仅在用户和运行时明确允许时并行委派。不能委派时，主 Agent 使用分离的串行轮次和独立记录完成同样工作；不得抽样、合并掉某组或省略跨组检查。

## 8. 评审完成门槛

`docs_only` 为真时，门槛替换为：精确范围新鲜、第 3.5 节检查集逐项有结论、`doc_references` 的每项异常已解释、问题清单通过机器校验。其余各条不适用。

其他情况，给出最终结论前必须满足：

- 精确范围和 patchset 仍然新鲜
- 每个变更组均被覆盖，没有未解释的文件
- 五个视角均为有证据的 `checked`、`risk` 或 `N/A`
- 每个高风险组已追踪失败场景，且组内确认第一个问题后没有就此结束该组发现：剩余迁移与二级反例仍逐条走完并记录结论
- 所有候选均为 `confirmed`、`open` 或带理由的 `rejected`
- 命中的每条二级反例均已追踪或记录不可达理由
- 已完成规定的复核轮次：小变更含证伪轮；大变更含高风险组的第二次发现轮与收敛前全局复核
- 已运行与风险相称的验证，或明确说明无法运行的原因
- 已执行跨组复核；不适用时说明原因

未满足时不得用 `LGTM` 掩盖覆盖缺口。应输出“无法完成可靠 Review”或“未发现已证实阻断问题，但存在待确认风险/覆盖限制”。
